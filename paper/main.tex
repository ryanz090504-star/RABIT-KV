% ============================================================================================ ABSTRACT
\begin{abstract}
Low-bit KV-cache quantization is usually described by its logical precision, but a serving system
benefits only when that bit budget becomes allocator capacity. Between the two lie costs that a nominal
bit-width omits: quantization metadata, full-precision residual tokens, partially filled groups, and
the online aging of cache state. We present RABIT-KV, a target-bit-aware, physically packed KV-cache
system that jointly accounts for asymmetric key/value precision, residual state, metadata, online cache
aging, and allocator capacity, integrated into the vLLM serving engine [vLLM]. On the evaluated H100
setup with Llama-3.1-8B, RABIT-KV provides $5.2785\times$ the physical KV capacity of BF16,
$2.6409\times$ that of FP8, and $1.724\times$ that of the tested TurboQuant configuration [TurboQuant],
at $+8.33\%$ median single-request time per output token relative to that configuration. Llama
continuation perplexity rises by $1.56\%$, NIAH and Passage Retrieval retain their tested scores, and
HotpotQA is approximately 1 F1 lower with a confidence interval spanning zero; Qwen2.5-7B, at the same
operating point, shows severe model-specific quality sensitivity. The current correctness-first
implementation does not convert its capacity advantage into higher throughput on the evaluated
workloads. Physical capacity, quality, and serving cost must therefore be evaluated jointly.
\end{abstract}

% ======================================================================================== INTRODUCTION
\section{Introduction}

% P1 -- motivation (claims: C1, S2)
Once model weights are loaded, the key--value (KV) cache is the main consumer of GPU memory in an LLM
serving system. It grows linearly with context length and with the number of in-flight requests, and a
paged allocator [vLLM] admits a request only when blocks are available for it. KV memory therefore
bounds how much context and how many concurrent requests one GPU can hold. Quantizing the cache is a
direct response [KIVI, KVQuant, TurboQuant], and such methods are commonly characterized by a logical
bit-width: the number of bits per stored key or value element. The quantity a serving system can use,
however, is physical: the number of tokens its allocator can place in a fixed memory budget. The two
are related but not interchangeable.

% P2 -- gap (claims: S1, S2, S3; novelty boundaries of evidence map section 12)
A nominal low-bit cache falls short of its bit budget for reasons that are individually well known.
Keys and values tolerate different precisions. Grouped affine quantization stores a minimum and a scale
per group, and at two or three bits per element this metadata is a substantial fraction of the payload.
The newest tokens are commonly kept at full precision. Groups are partially filled while a sequence is
being generated, and cache state must be re-encoded online as tokens age from one representation to the
next. The result must then fit the fixed-size blocks of the engine's allocator and be read by attention
kernels at an acceptable cost. Our focus is the systems problem of accounting for these effects jointly
and measuring the resulting allocator-visible capacity and runtime cost.

% P3 -- RABIT-KV and results (claims: S1, S2, C3, C5, L5, Q1, Q2)
RABIT-KV is a target-bit-aware, physically packed KV cache. One fixed operating point combines 3-bit
keys, 2-bit values, 32-element groups, a four-token full-precision residual window, and 8-bit quantized
group metadata, with an online lifecycle in which tokens age from the residual window into an open
group and then into closed, packed pages. The ``2-bit target'' denotes this operating point rather than
a literal end-to-end storage cost. The pages are stored in the paged allocator of vLLM [vLLM], and
capacity is reported as the number of tokens the engine allocates. On one H100 with Llama-3.1-8B,
RABIT-KV holds $5.2785\times$ the KV tokens of BF16, $2.6409\times$ those of FP8, and $1.724\times$
those of the tested TurboQuant configuration [TurboQuant], at $+8.33\%$ median time per output token
relative to that configuration in a matched single-request session. Quality loss on Llama-3.1-8B is
small (continuation perplexity $+1.56\%$), whereas Qwen2.5-7B shows severe sensitivity at the same
operating point; we therefore do not assume that quality transfers across models.

% P4 -- systems lesson and limitation (claims: T2, T3, T4, X4, P4, P6; frozen limitation wording I.5)
The broader lesson is that aggressive KV compression should be judged as a joint trade-off among
physical capacity, quality, and serving cost, not by nominal bits alone. RABIT-KV makes the cost side
explicit. Its capacity raises the admissible load: with 8192-token prompts, BF16 reaches its allocator
ceiling at 47 in-flight requests, whereas RABIT-KV sustains 64. Yet in every concurrency workload we
tested, RABIT-KV's throughput remains below that of BF16, and prompts that extend beyond the first
16,384-token prefill chunk incur a large time-to-first-token penalty. The current implementation
prioritizes correctness and physical packing over cross-request and cross-token kernel batching, so a
capacity gain does not by itself yield an end-to-end serving benefit. We report these costs alongside
the capacity result and leave a batched runtime to future work.

% Contributions -- THREE bullets (blueprint section 2)
\paragraph{Contributions.}
\begin{itemize}
\item \textbf{Design.} A target-bit-aware KV-cache representation with an online cache lifecycle
  covering asymmetric key/value precision, full-precision residual state, quantized group metadata,
  open groups, closed pages, and cache aging. Rather than treating these mechanisms independently,
  RABIT-KV integrates them into one lifecycle whose target bit budget maps to a concrete physical
  layout.
\item \textbf{Physical system.} A physically packed integration into the vLLM serving engine, whose
  benefit is measured as allocator-observed KV capacity rather than by logical compression accounting:
  $5.2785\times$ BF16, $2.6409\times$ FP8, and $1.724\times$ the tested TurboQuant configuration on
  Llama-3.1-8B, with the same ratio over BF16 on a second model geometry.
\item \textbf{Evaluation.} A matched systems evaluation across BF16, FP8, TurboQuant, and RABIT-KV,
  together with quality validation on Llama-3.1-8B and Qwen2.5-7B using an evaluator verified against
  an independent reference. It exposes the capacity gain together with its latency, throughput, and
  model-dependent quality trade-offs.
\end{itemize}

% ========================================================================== BACKGROUND AND MOTIVATION
\section{Background and Motivation}
\label{sec:background}

% claims: C1, S2 (bytes), C4 (TurboQuant configuration)
\paragraph{KV-cache memory.}
For every token, each decoder layer stores one key and one value vector per KV head. With $H$ KV heads
of dimension $d$, a token therefore holds $2Hd$ elements per layer. For Llama-3.1-8B ($H=8$, $d=128$,
32 layers) this is 4,096 bytes per token per layer in BF16, or 128\,KiB per token. The state lives as
long as its request, so KV memory grows with the product of context length and concurrency.

\paragraph{Paged allocation.}
Serving engines such as vLLM [vLLM] manage this memory as a pool of fixed-size blocks. A block holds the
KV state of a fixed number of consecutive tokens (32 in our configuration), and a per-request block
table maps token positions to blocks. The pool is sized once, at start-up: the number of blocks is the
KV memory budget divided by the bytes that one block occupies. A request is admitted, and can grow,
only while free blocks remain. Throughout this paper, \emph{capacity} means the number of blocks times
the tokens per block as reported by the running engine. It is the quantity the scheduler can use.

\paragraph{Logical precision is not physical capacity.}
Quantized KV caches [KIVI, KVQuant, TurboQuant] are usually described by the bit-width of their codes.
The bytes a block occupies depend on more than that. First, affine quantization stores a minimum and a
scale per group. With groups of 32 elements, two 16-bit parameters add one bit per element, which is a
third of a 3-bit payload and half of a 2-bit one. Second, some state is kept at full precision: recent
tokens in residual-window designs, or entire layers, as in the TurboQuant configuration we test, which
leaves four boundary layers in BF16. Third, when quantization statistics span several tokens, the group
at the end of a growing sequence is incomplete and has no final encoding yet. Whether each of these
costs is stored inside the block pool, beside it, or not at all determines how many blocks fit in the
budget. A bit-width alone therefore does not determine capacity; it has to be measured in the engine,
together with the runtime cost of reading the packed state.

% ================================================================================================ DESIGN
\section{RABIT-KV Design}
\label{sec:design}

% claims: S1, S2, S3, V6. FIGURE 1 goes here (lifecycle and page layout); not yet created.
RABIT-KV is defined by a single operating point, written K3\,/\,V2\,/\,G32\,/\,R4\,/\,META8g64. It was
fixed during earlier development and was not retuned for any experiment in this paper. We describe it
as one configuration, not as the best member of a tuned family, and we do not claim that each component
is individually optimal.

\subsection{Operating point}

\paragraph{K3: keys.}
Keys are stored as 3-bit affine codes grouped along the \emph{sequence} axis. For each (head, channel)
pair, 32 consecutive tokens form a group with one minimum and one scale, $s=(\max-\min)/7$.

\paragraph{V2: values.}
Values are stored as 2-bit affine codes grouped along the \emph{channel} axis. For each (token, head)
pair, 32 consecutive channels form a group with one minimum and one scale, $s=(\max-\min)/3$.

\paragraph{G32: group size.}
Both groupings use 32 elements. Thirty-two tokens are also the unit of physical storage: one K group
along the sequence, the values of the same 32 tokens, and their metadata form one page, and one page
occupies one allocator block.

\paragraph{R4: residual window.}
The newest four tokens of every sequence are kept exactly, in BF16.

\paragraph{META8g64: metadata.}
The minimum and scale arrays are themselves quantized. Each array is split into groups of 64 values and
stored as 8-bit codes with one BF16 minimum and scale per group. Keys and values are dequantized with
the parameters decoded from this second level, not with the original ones.

The two axes have different consequences. A value group lies within one token, so a token's values can
be encoded once, as soon as the token leaves the residual window, independently of every other token.
A key group spans 32 tokens, so its metadata is amortized over a page, with one minimum and scale per
(head, channel), but its statistics are not final until all 32 tokens exist. Keys also receive one more
bit than values. These choices define the lifecycle below; their effect on quality is measured only for
the operating point as a whole.

\subsection{Cache lifecycle}

% Figure 1: residual window -> open group -> closed page.
A token passes through three states (Figure~1).

\paragraph{Residual.}
A new token enters the residual window with exact keys and values.

\paragraph{Open group.}
When a fifth newer token arrives, the token leaves the window and joins the \emph{open group}, the
incomplete K group at the end of the sequence. Its values are encoded to their final 2-bit form. Its
keys cannot be: the open group is quantized as a 32-token group padded with zeros, so the group
statistics, and with them the codes of every key already in the group, are recomputed as the group
grows.

\paragraph{Closed page.}
When the open group reaches 32 tokens it closes. Its key codes and metadata become final, and the key
payload, the value payload, and the META8g64 metadata are written as one packed page. A closed page is
never modified again.

A sequence of $n \ge 4$ tokens thus consists of $\lfloor (n-4)/32 \rfloor$ closed pages, an open group
of $(n-4) \bmod 32$ tokens, and four residual tokens. Once this state exists, attention reads all
three: closed pages and the open group in quantized form, the residual window exactly. (The serving
engine computes the initial prefill of a prompt over exact keys and values before it builds this
state; Section~\ref{sec:impl}.) Aging is online. It happens as tokens are
appended during prefill and decoding, there is no offline compression pass, and the representation of a
key keeps changing until its group closes. This is why we validate the lifecycle token by token and not only
its final state (Section~\ref{sec:method}).

\subsection{Physical accounting}

We distinguish four quantities that are often conflated.

\paragraph{Target-bit label.}
``2-bit target'' names the operating point. It is not a storage cost.

\paragraph{Logical payload bits.}
A token has equally many key and value elements, so 3-bit keys and 2-bit values give 2.5 payload bits
per element.

\paragraph{Physical page bytes.}
For one layer, a page holds $32Hd$ key elements and $32Hd$ value elements: $12Hd$ bytes of key payload
and $8Hd$ bytes of value payload. There are four metadata arrays (minimum and scale, for keys and for
values), each with $Hd$ entries per page: one per (head, channel) for keys, and one per (token, head,
channel group) for values, which is $32 \cdot H \cdot d/32$. Stored directly in BF16 they would take
$8Hd$ bytes, 40\% of the payload. Under META8g64 each array takes $Hd$ bytes of codes plus $Hd/16$ bytes
of group parameters, $4.25Hd$ bytes in total. A page therefore occupies $24.25Hd$ bytes per layer. For
Llama-3.1-8B ($Hd=1024$) this is 24,832 bytes per page, or 776 bytes per token per layer, against 4,096
bytes in BF16. Dividing by the $2Hd=2048$ key and value elements of a token in one layer gives about 3.03 bits per
element. This is a derived, closed-page figure and not our headline metric. It counts payload and
metadata of closed pages only. It excludes the residual window, the open group, and any rounding by
the allocator.

\paragraph{Allocator-observed capacity.}
The number of tokens the engine can place in its KV budget is the quantity we report as the result. The
page bytes above predict a ratio of $4096/776 \approx 5.28$ over BF16. Section~6 reports the value
measured in the running engine and compares it with FP8 and with the tested TurboQuant configuration.
This capacity measures the paged KV pool. The residual window and the open group are per-sequence
state of at most 35 tokens, held outside the pool and not counted in it, so the capacity ratio is not
a statement about total device memory including all auxiliary state of active sequences.

% ================================================================================ PHYSICAL IMPLEMENTATION
\section{Physical Implementation}
\label{sec:impl}

% claims: C3, V1, L6, X4, P4 (design fact only)
\paragraph{Integration.}
RABIT-KV is implemented as an additional KV-cache type in the Triton attention backend of vLLM [vLLM].
The scheduler, the block allocator, and the per-request block tables are unchanged. The engine sizes
its block pool from the bytes per block, so declaring the packed page size as the block size is what
turns the representation into capacity: the same memory budget yields more blocks, and the scheduler
admits requests against them as it does for any other cache type. There is no separate compressed pool
and no background compaction.

\paragraph{Packed pages and per-sequence state.}
One allocator block holds one closed page per layer: packed 3-bit key codes, packed 2-bit value codes,
and the four META8g64 metadata arrays. A page is written into its scheduler-assigned block at the
moment its group closes. The residual window and the open group are kept in a small per-request
structure outside the pool. It is bounded by 35 tokens per sequence.

\paragraph{Execution paths.}
Three paths read and write this state. \emph{Initial prefill:} for the first prefill chunk of a
request, attention is computed densely over the exact keys and values of the chunk, and the chunk is
then encoded in bulk into closed pages, an open group, and a residual window. \emph{Later prefill
chunks:} when a prompt exceeds the per-step token budget (16,384 tokens in our configuration), or when
that budget is shared among requests, the remaining tokens attend to the already packed prefix and to
the exact tail under the causal order of the chunk; the decoding of closed pages is shared by blocks of
32 queries. \emph{Decode:} each new token is appended, the lifecycle of Section~\ref{sec:design}
advances by one step, and attention is computed in parts: over the closed pages, which are dequantized
inside the kernel and never materialized in full precision, over the open group and the residual
window, and a final reduction that combines the partial results.

\paragraph{What is not batched.}
In the current implementation these paths run once per request, and append, aging, and the open-group
work run once per token. Requests in the same scheduler step are processed one after another within
each layer, while the rest of the model is batched as usual. The implementation was built for
correctness and physical packing first. Section~6 measures the consequence for latency and throughput.

\paragraph{Model geometries.}
The kernels are specialized for the Llama-3.1-8B attention geometry. Qwen2.5-7B has a different head
layout (four KV heads) and is served through exact general fallback paths: the same representation, pages, and capacity
accounting, executed by unspecialized code. Its latency therefore measures the fallback paths and is
not evidence about how the specialized kernels would transfer.

\paragraph{Correctness.}
A fixed test suite is run before every serving experiment. It checks the page layout, the page codec
against a reference implementation, the online state against that reference at every step, the
metadata encoding, grouped-query attention, and causal chunked prefill. These tests establish agreement
with the reference on the tested cases; they are not a formal verification.

% =========================================================================================== METHODOLOGY
\section{Experimental Methodology}
\label{sec:method}

% claims: C1-C6 (method), L1 (method), T1-T4 (method), X1 (method), V2-V7, Q1-Q8 (method)
\paragraph{Setup.}
Every run uses one NVIDIA H100 (80\,GB). The engine is a vLLM snapshot [vLLM] with our changes, in eager
mode, with 32-token blocks, a GPU memory fraction of 0.82, and a maximum model length of 32,768 tokens.
The models are Llama-3.1-8B-Instruct [Llama3.1] and Qwen2.5-7B-Instruct [Qwen2.5] at pinned revisions with BF16
weights. Baselines are the BF16 cache, the engine's native per-tensor FP8 cache, and one TurboQuant
configuration [TurboQuant] that quantizes 28 layers and keeps four boundary layers in BF16. TurboQuant
runs with its own attention backend, so comparisons with it are between systems as deployed, not
between quantization kernels.

\paragraph{Physical capacity.}
Capacity is read from the running engine as the number of allocated blocks times 32 tokens, under the
same memory budget for every method. It is not computed from byte estimates.

\paragraph{Latency and throughput.}
Absolute latency varies between sessions, so methods are compared only within one session. The primary
comparison serves all four methods in a mirrored order (A\,B\,C\,D\,D\,C\,B\,A), two legs per method
and 30 single-request samples per leg, with a 2048-token prompt and 32 greedily decoded output tokens.
We report medians of time per output token (TPOT) and time to first token (TTFT); these statistics are
descriptive and carry no confidence intervals. Context scaling uses single requests with prompts from
512 to 32,736 tokens and 15 samples per cell. Concurrency uses a closed loop at 1 to 64 in-flight
requests with 2048- and 8192-token prompts, 256 measured requests per point after unmeasured
conditioning, and three trials per point.

\paragraph{Quality evaluator.}
Quality is measured logically, outside the serving engine, with a cache object for Hugging Face
Transformers [Transformers] that implements the representation and lifecycle of
Section~\ref{sec:design}. Serving and logical evaluation use different execution machinery: the
evaluator reproduces the stored-cache representation and its aging, not the serving kernels or their
schedule. Every evaluation has two phases. The prompt is processed in one dense BF16 forward pass, so
prompt tokens attend to exact history, as in the initial prefill of the serving engine. The resulting
keys and values are then converted in one step into the RABIT-KV state for that length: closed pages,
an open group, and four residual tokens. Every later token is processed one per forward pass. It is
appended, the lifecycle advances, and the token attends to the state at its own position, so no token
stays exact beyond the residual window. The BF16 arm runs the same loop on the same inputs with an
unmodified cache.

\paragraph{Tasks.}
Continuation perplexity is measured on WikiText-2 [WikiText] for both models, over 32 windows of 1,024
context tokens and 128 scored tokens. The first scored token is predicted by the BF16 prefill and is
identical in both arms; the other 127 are teacher-forced against the RABIT-KV state. Long-context
quality is measured for Llama-3.1-8B only, with greedy decoding: needle-in-a-haystack retrieval [NIAH]
(57 cases at 4,096, 8,192, and 16,384 tokens) and the Passage Retrieval (200 examples) and HotpotQA
(100 examples) tasks of LongBench [LongBench, HotpotQA]. Here all but the last prompt token are
prefilled and the last prompt token is the first step on the converted state, so every generated token
is predicted from RABIT-KV state. Prompts are at most 16,384 tokens and the evaluator never executes a
later prefill chunk. The quality of prompt tokens that attend to an already packed prefix, which occurs
in serving beyond the per-step token budget, is therefore not measured. Confidence intervals are paired
percentile bootstraps with 10,000 resamples.

\paragraph{Validation against an independent reference.}
The state transformation and aging computed by the evaluator were checked bit for bit against an
independently written, frozen reference implementation, on the same device. The check covers synthetic
states, including token-by-token aging, and the keys and values the models actually produce on the GPU:
every layer of both models, and a 16k-token context for Llama-3.1-8B. CPU and GPU arithmetic differ in
the last bit of some scales, which moves a small fraction of codes by one level, so conformance is
established on the device that runs the evaluation and we define no cross-device tolerance. This check
establishes that the evaluator computes the intended stored state. It is not a formal verification, and
it says nothing about model quality or serving performance. The serving implementation is tested
against the same reference (Section~\ref{sec:impl}); we do not compare serving outputs with evaluator
outputs end to end.

\paragraph{Registered protocol.}
Each quality run is frozen before execution: inputs, example selection, scorers, bootstrap seeds, and
the rules for interpreting the outcome. Nothing is tuned in response to results. Validity checks on
output quality use only BF16 outputs, and a run that fails a validity check is excluded.

\paragraph{Scope of the quality evidence.}
Earlier development results were produced with an evaluator that did not implement this lifecycle
exactly: it ordered the value metadata differently, and it quantized the prompt once without aging
generated tokens. We report quality only from the validated evaluator, never pool the two, and place
the earlier results in the appendix, labeled as such.
